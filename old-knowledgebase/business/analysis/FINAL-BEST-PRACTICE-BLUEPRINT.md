# FINAL BEST-PRACTICE BLUEPRINT — GeoQuest Rebuild (Conceptual, Pre-Implementation)

**Status:** Living document. Started from parallel adversarial ANALYZE-* slices (GAMSTEP-03, COINS-04, CONSTRUCTOR-07, OFFLINE-01 + reviewers + main-thread synthesis). Will incorporate remaining (06 commerce, 08 answers, 10 sync, 11 domain, 12 nonfunc) + full cross-review as they complete. All under TDD/SOLID/DRY/KISS/YAGNI + extreme skepticism. Grounded exclusively in business/ foundation + discovery/parsed (old as cautionary noise, not spec).

**Purpose:** Maximum documentation of what the project *will be like* and *why*. Every major business feature/requirement has:
- Current locked (from 08_DECISIONS_LOG + prior conversation).
- Multiple approaches considered (from subagent variants + main review).
- Chosen best-practice (with rigorous rationale: robustness, maintainability, elegance, constraint satisfaction, improvement over old Bubble mess and initial proposals).
- Rejected alternatives (with why).
- Cross-slice interactions, invariants, risks, migration notes, conceptual tests.
- How it enables long-term highest readability/maintainability.

**Overall Principles (synthesized so far, to be hardened):**
- Content & semantics are versioned immutable snapshots at publish time (frozen for attempts that started against them).
- Client is authoritative for its snapshot lifetime (full local validation, no server correctness re-val on sync) — but with tamper-evident receipts/hashes + server records facts for audit/analytics.
- Progress/earnings are append-only facts/events (idempotent, replayable, conflict-free merge on multi-device/offline).
- Rich content is the primary differentiator for player experience/atmosphere; completion rules + supporting are small data.
- One clean GameStep shape (no 14 Page_types, no 36-field multilingual explosion, no answer_card flag bag).
- Constructor is small, typed, data-first (form+list baseline + strengthened gates + plan for import); publishing is the "hard" explicit step that produces the bundle shape.
- Economy is lightweight but robust (event facts, not mutable scalars; snapshot-frozen amounts; per-attempt tracking + global projection).
- Commerce is simple lifetime grants (idempotent, source-audited, single checkout v1).
- All slices converge on: explicit publish for version, server retains historical snapshots/manifests (indefinite for active attempts), client bundle is the contract for offline.

**Structure:** One section per major area (from master todo + business/ docs). Each ends with "Chosen + Why" + "Documentation references".

## 1. GameStep Model, Completion Semantics, Physical vs Answer-required, Supporting Types (from ANALYZE-03 + main synthesis + reviewer cross)

**Locked (08 + 03/04/01):**
- Two primary: Physical (uniform explicit confirmation "I did it" + optional note; no acceptable list; trust honesty; geo display only) vs Answer-required (list of strings from multiline constructor input; client membership match against snapshot).
- Supporting as flags/combos (gift with coins, hint coin-gated geo reveal, media/video, terminal, narrative advance, etc.).
- Linear sequence only (v1).
- Rich content (main/place/question/hint/gift text, media, geo) carries atmosphere/differentiation.
- All frozen in snapshot at publish; old attempts use their version's rules/amounts.
- Coins earned via gifts (per GameStep) + completions (e.g. 5-coin bonus, first-only via de-dup).

**Approaches Considered (full cycle in subagent report + main review):**
- V1: Current lean (primary mode + supporting flags, uniform physical).
- V2: Richer first-class kinds (physical_observation/action/counting, knowledge/puzzle, etc.; 14+ inspired by old Page_type).
- V3: Content-driven + embedded CompletionRule (small discriminated: ConfirmationRule | AnswerListRule | null; supporting as composable object).
- V4: Strategy/composition per step (CompletionBehavior + SupportingBehaviors[] as data + small handlers; registry for pluggability).
- Main synthesis refinement (post-review): Pure discriminated data shape on the step (no named "Rule" types in v1 data model to avoid ceremony/YAGNI): completion: { mode: 'physical' | 'answer', acceptable?: string[], allow_note?: bool } + supporting: { gift?: {coins, narrative}, hint?: {cost, reveal...}, ... } validated at authoring. Rich content primary. Extensible later by adding to the object or new supporting keys. This captures V3 benefits (explicit semantics per step/version, future NumericRange/Photo without mutating core) while staying leaner than full objects or taxonomy.

**Chosen Best Practice:** The refined lean data shape (content-first + small discriminated completion data + composable supporting object).

**Why (rigorous, under constraints + skepticism):**
- Fully respects *every* locked (uniform physical confirmation mechanism + note, list strings for answers, client local match for offline snapshot, linear, snapshot freeze, coins via gifts from GameStep).
- Directly attacks key risks exposed in 07/03 self-critiques and deconstruct ("no difference physical reduces the magic" — rich per-step content + custom button text + images provide differentiation; "list may not scale to puzzle variety" — adding numeric_range or interpretive fields later doesn't require new primary mode or flag explosion).
- Maintainability/readability win vs old (one GameStep shape + tiny attached data vs 14 overloaded Page_type driving 14 specialized Slide_* reusables + 3-21 WFs each + 444 SetCustomState + answer_card flag bag + scattered coin logic in "steps_for_accruing_coins_" + "666" WFs). 556 steps become uniform instances; migration is straightforward Page_type + Answers-presence + Gift_Coins mapping.
- Vs pure locked lean: makes semantics explicit and versionable ("this step used Confirmation + allow_note" in the frozen snapshot); better for analytics per-version; prepares extensibility without violating KISS now.
- Vs richer kinds (V2): avoids recreating taxonomy bloat (only add if real usage data from 21 quests shows the 14 were all heavily differentiated in player/author experience).
- Vs full V3/V4 objects: the data shape is the "embedded rule" without premature naming or indirection cost for v1 (where 80%+ will be the two primitives). Still extensible (add fields to completion or new supporting keys; small handlers in player/constructor).
- Offline/bundle fit: serializes cleanly (completion data + answers list plainly + supporting amounts frozen). Constructor data entry (multiline or structured list for answers; number for gift_coins) directly produces it.
- Cross-slice: Aligns with COINS (gift amounts from snapshot GameStep, emitted on StepCompletion record); CONSTRUCTOR (publish must snapshot the exact shape; strengthened gates for answers list + gift entry); OFFLINE (client validates against the data in its bundle).
- Constraints: KISS (minimal data, no 14 types); YAGNI (no photo/geofence/branching now; no heavy objects); SOLID (single shape, small discriminated for completion); DRY (supporting composable, not duplicated per kind); maintainability (one shape, versioned data, centralized handlers, testable).
- Risks accepted: Mild extra shape vs "two modes only" (but still far simpler than old); must rigorously validate combos in constructor; "maintainability" claim to be proven in actual code (not just first-principles + historical pain).

**Rejected & Why:**
- Pure locked lean (V1): Compliant but directly inherits "trivial confirm reduces magic" and "list doesn't scale" (explicitly flagged in sources). Flag combos can create nonsense; still requires branching in render/validation.
- Richer kinds (V2): Re-creates taxonomy bloat immediately (per-kind renderers, constructor panels, migration cases). YAGNI for v1; speculative without real Page_type usage counts from 556 steps.
- Full V3/V4 without lean refinement: Adds ceremony (named objects, registry) that may exceed benefit if most steps are simple. Risk of over-engineering for small internal team.

**Invariants (updated):**
- Exactly one primary completion mode per step.
- Supporting additive + authoring-validated (no invalid combos).
- All completion/supporting data (acceptable list, gift coins, hint cost) frozen in the quest snapshot at publish.
- Rich content is the variable/atmosphere carrier; completion data is the minimal mechanism.

**Migration notes:** Old page_type + Answers list presence + Gift_Coins → completion.mode + acceptable (if present) + supporting.gift. Old answer_card flags → StepCompletion (player_confirmed or submitted + local outcome per version).

**Conceptual tests:** Per-mode validation; combo invariants; snapshot freeze (v1 gift_coins used even if live quest changed); rich content renders differently for two physical steps with same mode.

**Documentation refs:** business/01 (updated GameStep), 04 (updated data + constructor), analysis/gamestep-completion-variants.md + review-gamestep.md + SYNTHESIS-NOTE-....md.

## 2. Coins / Hint Economy & Earning Mechanics (from ANALYZE-04 + cross + main review)

**Locked (08_DECISIONS_LOG + 01/03/06/07):** Earnings exclusively via gifts defined in GameSteps (Gift_Coins from the bound snapshot) + completions (e.g. 5-coin bonus, first-only via de-dup like old Getting_5 list). No admin manual adjustments (v1). No real-money coin purchases (v1). Spend = per-step hint buy (deduct cost, mark revealed for that StepCompletion; geo + hint content shown only after). Per-attempt spends tracked in StepCompletion; master player balance = sum of earnings from completed quests/gifts minus spends (reconciliation on sync). Offline: local award/spend + projection from snapshot + local state; server authoritative on sync + corrections (e.g. overdraft). Snapshot-frozen amounts for old attempts. "steps_for_accruing_coins_" intent (old accumulator on congrats) must be made explicit.

**Old Bubble Reality (Heavily Mined from Discovery, per Report §2):** Not a clean domain rule — scattered mutations. Gift_Coins (number) on page_constructor awarded on "gift" Page_type / Slide_give_prize. 5-coin completion bonus on "You_made_it"/Complited_quest/terminal (Slide_Congratulations with 9 WFs + "steps_for_accruing_coins_" custom state). De-duped via user.Getting_5_coins_for_completing list<quest>; countCoinMadeIt on quest. Spend: Buy_hint (bool) flag on answer_card (per User + Page_constructor step + Quest) + immediate Change on user.Balance_coin (global scalar). Tracking: global user.Balance_coin; "per-attempt-ish" via answer_card bag (Buy_hint + Complited/You_made_it/Complited_quest/Count_wrong_answers — mutated by dozens of imperative WFs in 82 quest-page + reusables). Old had zero versioning/snapshots/offline (mutable content, always-online assumption via API events + direct mutations). "Accruing" was UI custom state + scheduled WFs ("666" family etc.). No audit log, no idempotency model, no per-snapshot freezing.

**Approaches Considered (Full Cycle in Report §5 — Deconstruct/Exposed/Rebuilt/Self-Critiqued Each):**
- V1: Simple global balance + event log of earns/spends (current lean minimally extended; append-only CoinEvent tied to attempt+step+type+snapshot; balance = projection/sum; optimistic/pessimistic tx + uniques for races; offline local projection from snapshot + local state; server facts + corrections).
- V2: Per-attempt coin wallet (scoped attempt_coin_balance for earns/spends during the QuestAttempt; global = sum or banked post-conversion; conversion? offline clean per-attempt; races isolated but conversion + same-attempt multi-device still risky; old data was global Balance_coin + per-card flags, not clean wallet).
- V3: Step-reward as first-class immutable events projected to balance (RewardEvent emitted on authoritative StepCompletion for gift/terminal — amount frozen from bound snapshot; idempotency_key = attempt+step+kind; Spend facts on completions; balance = fold/projection; offline: client projects from snapshot + local completions; server emits facts idempotently on sync + returns authoritative + corrections; facts union cleanly).
- V4: Capability-based hints without numeric balance (or non-fungible "hint tokens"; earn unlocks/uses per (player,quest,step) or global set instead of scalar; Buy = check/decrement uses, mark revealed; no arithmetic races/negative/overspend structurally; offline trivial (local set); maximum robustness but radical product change).

All variants respect locked (earnings only gifts/completions from snapshot; per-attempt spends; master reconciliation; offline local + server; no admin/real$ v1; first-only de-dup). Full edge/race/ accounting/ offline-fit/ pros-cons/skepticism applied (e.g., V1 too easy to regress to imperative scalar + optional log = old debt in new code; V2 UX damage for cross-quest hints + extra conversion races + mismatch to old global data; V4 maximum robustness but changes "coins" mental model/UX/language in all docs + existing app from 929 users/21 quests; migration lossy; less flexible for variable costs or future real$).

**Chosen Best Practice (Main-Thread Review + Cross-Slice Alignment):** Variant 3 (immutable step-reward events projected to balance), augmented with materialized view (V1-style for fast reads) + narrow unique facts for first-only de-dup (V4 flavor where needed). 

**Why (Rigorous — Robustness First, Then Maintainability, Under All Constraints + Skepticism):**
- **Robustness (No Lost/Double Coins — Addresses Every Race from Deconstruct):** Immutability + natural idempotency keys (tied to the StepCompletion that is *already* the authoritative sync record) structurally prevents double-earn (unique on attempt+step+kind + snapshot) and lost-earn (missing fact for a recorded completion). Projection ensures "master = sum earnings - spends" is never a lie (drift = projector bug, not data). Versioned gifts: solved — amount frozen in the fact at emit time from the attempt's snapshot (critical per OFFLINE/GAMSTEP; old had zero versioning). Races minimized: no "read balance, decide, write" for earns (facts emitted on completion record); spends are 1:1 facts on StepCompletion (per-attempt, per-step). Multi-device/offline/sync: facts union cleanly (no last-write ambiguity); client projection is best-effort provisional (server authoritative on sync + explicit corrections, e.g. "overdraft detected, hint un-revealed, balance adjusted"). Negative only via import bugs or explicit correction events (normal path cannot produce). Concurrent earns (e.g. bonus): unique constraint or existence check before emit. Reset: clears attempt progress/StepCompletions but not already-emitted global rewards (banked facts survive). Import: synthesize historical facts once (idempotent job from old Balance_coin + Getting_5 list + Buy_hint on answer_cards + Gift_Coins on page_constructor); log diffs vs old scalar for manual review (no auto-adjust). Overspend: client may provisional; server records facts, projects, corrects.
- **Maintainability / Clear Accounting (vs Old Scattered Mutations + Future-Proof):** Events are self-documenting/auditable/replayable: "this gift step in vX of quest Q awarded 10 to this player on this attempt at this time because this StepCompletion was recorded (using snapshot-frozen amount)." "steps_for_accruing_coins_" becomes explicit query on rewards for quest+version+attempt. Easy analytics ("earnings by gift step"), admin visibility (read-only), replay for audit ("what was balance on date D?"), import synthesis. "Accruing" logic centralized (no reverse-engineering 82 WFs + 9 on congrats slide + custom states). KISS at the right layer: simple domain rule ("rewards are consequences of recorded step facts in a snapshot") + necessary machinery (events + projector); no accidental complexity. Better than old (scattered ChangeThing in UI state machines + scheduled "666" + no audit/versioning/offline) and pure scalar (recreates races/debt). Extensible for future real-$ (add 'PURCHASE' event types; v1 forbids) or richer economy without mutating core.
- **Fits All Locks + Cross-Slices (No Contradiction):** Earnings only from gifts/completions (exact timing/amounts from old behavior, now explicit via StepCompletion record + snapshot). Per-attempt spends (on StepCompletion) + global projection/reconciliation. Offline local award/spend + server reconcile/corrections (client projects from snapshot gift defs + local completions; facts uploaded on sync). Snapshot-frozen (amounts in facts from bound snapshot; aligns with GAMSTEP GameStep + OFFLINE bundle). No admin/real$ (v1). First-only de-dup via unique fact (like old list, but clean). Ties to GAMSTEP (earnings emitted on authoritative StepCompletion for gift/terminal steps, using snapshot GameStep gift amounts; "You_made_it" / terminal triggers bonus). Ties to CONSTRUCTOR (gift_coins entered per step in authoring; publish snapshots frozen amounts into the GameStep data in bundle). Ties to attempts/sync (facts on completions; per-version). Improves "lightweight" UX (still numeric balance for players) while fixing system races (old global scalar + immediate mutations = double-spend/negative/overspend/import hell).
- **Why Not the Others (Skeptical Critique from Report + My Overlay):** V1 without first-class events: too easy to regress to imperative scalar mutation + "log for debug" = recreates Bubble debt in Rust/Next (explicitly warned in 09_WHY + report). V2: adds conversion complexity/scoping decisions that locked docs + old data do not clearly support (old was global Balance_coin + per-card flags, not clean per-attempt wallet); risks fragmenting cross-quest hint economy (earn in easy quest, spend in hard?); UX damage if non-convertible; extra races on conversion. V4: maximum robustness (eliminates entire numeric arithmetic race class; no negative/overspend possible structurally), but radical product change vs grounded intent ("coins", Balance_coin, "in-game coin balance", Gift_Coins values, "buy hint with coins" UX everywhere in docs + existing app from 929 users/21 quests). Changes mental model; migration lossy (numeric Balance + per-card Buy_hint doesn't map 1:1 to unlocks without heuristics); less flexible for variable costs or future real-$ / tradable; may not match "lightweight economy" player expectations. Use only if numeric races prove unmanageable post-impl (or for a future simplified-hints mode). Hybrid (V3 + materialized + V4 narrow unique for bonus) is the pragmatic winner.
- **Trade-offs Accepted (Under Constraints + Skepticism):** Slightly more concepts/tables (events + projector) than pure scalar (but necessary for robustness/audit/versioning; "simple" in name only if it regresses to mutation). Client must implement correct local projector (but already required for answers per locked offline model + GAMSTEP; test with golden fixtures). If scale is tiny (<100 players) and no one ever complains about coin bugs, a simpler scalar + heavy tx in 2-3 endpoints could "work" — but we are building for the next 5+ years + import + multi-device/offline + races, not the demo. "Lightweight" preserved for players (numeric balance UX); robustness for the system. No over-engineering (V4 rejected for product fidelity).

**Invariants (Hardened from Report §6 + Cross-Slices; Enforceable in Types/Tests/Projection):**
- All coin rewards originate exclusively from GameStep definitions in a specific quest snapshot (gift_coins amount on the step) or the canonical completion bonus. No other sources.
- A reward fact/event for a specific (player, quest, reward_kind, [step]) is emitted at most once (idempotent; first-only for bonus via unique on (player, quest, 'COMPLETION_BONUS') or existence check before emit).
- Hint spend facts are 1:1 with a StepCompletion for that step in that attempt; a step cannot be "bought" twice for the same attempt.
- Player-visible balance (or available hint uses) is always a faithful projection of the immutable reward/spend facts. Never mutated directly.
- For any attempt, all rewards/spends during its lifetime use only the gift amounts and rules from the quest snapshot/version bound to that attempt.
- Admins have no API/UI to create/delete/adjust reward/spend facts or balances (v1; enforced by role + no such endpoints).
- No real-money purchase events for coins (v1).
- Offline local decisions (can buy? displayed balance) may be provisional; server reconciliation on sync is authoritative and may correct (reveal state, effective balance, compensation events).
- Reset of an attempt clears its StepCompletions and any un-banked per-attempt state, but does not retroactively revoke already-emitted (global) reward facts.
- On import of old data: historical rewards/spends are synthesized exactly once as immutable facts; the starting balance (if using scalar) or projection matches old Balance_coin only after import events (or we accept/log drift and let future play correct via earnings).
- Balance (projection) may temporarily appear negative only due to import bugs or explicit correction events; normal operation + client/server checks prevent it.
- Multi-device / concurrent operations converge to the same set of facts (no lost or double rewards/spends).
- Projection must be deterministic and match between client (for offline) and server.

**Race Mitigations (Detailed in Report §7 + Cross; Model-Agnostic Where Possible):**
- Idempotency first-class: every potential earn/spend carries natural/generated key (attempt_id + step_position + action_kind + client_ts or uuid). Server/sync: "if fact with key exists, return it; else create."
- Unique constraints at DB: (player_id, quest_id, reward_kind) for bonuses; (attempt_id, step_position, action_kind) for per-step.
- Transactions for check-then-act (where numeric): compute-projection + conditional insert in serializable tx or SELECT FOR UPDATE. Prefer facts (V3) to minimize.
- Event sourcing / append-only facts: preferred (facts don't race; projections do — but disposable + recomputable).
- Sync payload: upload list of StepCompletions (enriched with coins_spent_on_hint, hint_revealed, client-computed earned_if_accepted). Server processes in stable order, emits rewards/spends, returns true projection + delta/corrections + which accepted/rejected.
- Correction protocol: if server rejects spend (overdraft) or withholds reward (duplicate), client rolls back local UI state for that step/attempt on next load or via push. Display "syncing..." + "balance corrected".
- Multi-device merge: facts unioned by key. Conflicting reveals on same step: once revealed (any device), stays. Balance-affecting: facts determine.
- Import special: bulk "create historical facts" job with its own idempotency (per old answer_card id). Run once. Post-import, one-time projection vs old Balance_coin + log discrepancies for manual review (no auto-adjust).
- No direct scalar mutation: even in lean, only via fact append. Background job or on-read maintains materialized_balance (with checksum vs log).
- Version binding: all reward computations read gift amounts exclusively from the snapshot json stored with (or referenced by) the QuestAttempt / StepCompletion. Never from current quest GameSteps.
- Client local projection contract: PWA must implement *exactly* the same fold as server for data in one snapshot + local attempt state (test with golden fixtures from real quests).
- Monitoring: alerts on "projection < 0 for player without recent import", "duplicate reward attempt logged", "sync correction rate > X%".

**Offline Fit (Per Locked 03 + Cross with GAMSTEP/OFFLINE):** Download bundle includes full GameStep list with (for gift steps) their coin award amount (frozen from publish) + "this step has hint cost: X" flag. Local play: maintain per-attempt local state (completed, submitted, coins_spent per step or used unlocks, local_projected_balance). On gift/terminal: locally award (add to projected). On buy hint: if local_projected >= cost, set spent, deduct, reveal locally (pure client). Gifts/earns "pending until synced" but visible. On sync/reconnect: upload StepCompletions (enriched with coins_spent, revealed, local earned); server records, emits rewards for any gift/terminal per snapshot amounts (idempotent), records spends, returns true current balance/uses + corrections (e.g. "step 7 hint spend duplicate, not applied; balance +1"). Client applies corrections to local state + global cached. Versioned offline: old attempt uses its old bundle's gift amounts for local earning projection + what server will emit. No connectivity edge: player can exhaust local "coins" on hints, complete, earn more locally from gifts, continue spending in same session. All provisional until sync. Fits all variants (V3 events make facts explicit; V2 scopes to attempt local; V4 uses unlock sets — even simpler local state).

**Conceptual Tests / TDD Enablers (From Report §9 + Cross + My Additions):** 
- Unit/projection: Golden fixtures from 2-3 real quests (export page_constructor with Gift_Coins, simulate playthrough with gifts at positions + terminal; compute expected rewards per policy; assert projection matches). "Fold correct": given reward + spend events, balance == sum pos - sum neg. Idempotent re-fold.
- Idempotency/duplicate: Call "record completion for gift step" twice (same attempt+step) → only one reward. Two devices upload same spend for same step → one accepted. Re-complete after reset on same attempt → bonus not re-emitted (first-only).

Two concurrent completions for bonus on first play: exactly one bonus event (tx or unique). Spend while sync in flight: client local allows, server corrects.
- Property-based: Generate random sequences of earns/spends/resets/syncs for a player; assert never negative in final projection, total earned == sum of gift amounts from "completed" steps (modulo first-only), versioned amounts used correctly, no duplicate facts.
- Offline + sync: Play fully offline (multiple hints bought, gifts passed, congrats hit) → local balance updated. Sync → server events emitted, returned balance matches local (or corrected predictably). Re-load attempt sees correct reveals + balance. Bundle re-dl works for cleared client with in-progress.
- Admin/constraint: Attempt by admin role → denied. No purchase path.
- Replay/audit: From genesis events, replay to any point → balance at that point correct. "Total earned from gifts in quest Q" query works.
- Old equivalence (migration validation): For historical play (if full answer_card export), new facts explain old Balance change (modulo import correction).
- Version freeze: Same completion on v1 snapshot emits 10; live quest now has 0 for that step → still emits 10.
- Performance: Projection from 10k events fast (or materialized + checksum).

Run in CI against sync/completion services + client projection. Use real quest exports as fixtures. Adversarial sequences for long offline + multi-device + reset + version change.

## 4. Offline PWA Snapshot & Validation Model (from ANALYZE-01 + cross)

**Locked (03 v0.2 + 08):** Client downloads ~5MB self-contained snapshot (full GameSteps + plain acceptable answers list for answer steps + version + hash). Full local validation against that snapshot for attempts started from it (answer membership; physical explicit confirm). Server records submitted + *client-computed is_correct* + coins_spent + ts per (attempt,step,version) on sync — **no server re-val of correctness**. New = latest published; old attempts frozen to their snapshot. Physical = simple confirm (trust). Sync = record + coin reconcile + per-version analytics. Bundle enables full offline play.

**Approaches (from report, full cycle):**
- (Summary from partial + subagent meta): Locked baseline (plain strings + client judge).
- Approach 2 refined: Normalized content-addressable immutable step/answer entities (dedup storage, partial updates).
- Approach 3: Receipted/tamper-evident local claims (hashed acceptable sets + client-generated hash-chain receipts) + append-only event-sourced local progress + explicit server snapshot manifest retention.
- Hybrids + others (e.g., capability for some validation).

**Chosen (per report rec + main alignment):** Hybrid of normalized immutable + tamper-evident receipts/hashed sets + event-sourced local progress + explicit manifest retention policy + deterministic per-(attempt,version,step) merge on sync.

**Why:** Improves robustness over locked without violating "client local + no reval" (receipts provide post-facto audit/tamper detection; hashes prevent trivial edit of plain strings; events for superior merge/conflict-free on multi-device/long-offline + reset/replay). Storage deduped (YAGNI full copies today but future-proof). Clear error recovery, quota handling, coin tie-in. Maintainability: crisp aggregates (QuestSnapshotManifest, StepVersion, AnswerSetVersion with hashes, QuestAttempt bound to snapshot, StepCompletionFact, CoinReconciliationEvent). Fits GAMSTEP (validation against the data/rules in snapshot), COINS (events for earns/spends, snapshot-frozen amounts), CONSTRUCTOR (publish emits the exact shape with hashes/receipt support), sync/attempts (event-sourced local + deterministic server apply).

**Key improvements vs locked:** Addresses tamper (plain strings too naive even if "deprioritized"), freeze of errors (receipts + analytics help authors), multi-device (events better than last-write/union), retention (explicit manifest policy), client bugs (receipts + server facts for audit).

**Cross:** Bundle shape must include the refined GameStep (GAMSTEP) + frozen gift amounts (COINS) + support for receipts/hashes. Constructor must emit it (with validation). Publishing (parallel) must produce manifests. Sync payload includes facts + receipts.

**Risks accepted:** Some client complexity for receipts/projection; retention policy cost (but required for recoverability per locked).

## 6. QuestAttempt, Replay, Reset, Continue, Multi-Device & Sync (from ANALYZE-05 + cross + main review)

**Locked (from 01/03/08 + 06 risks):** QuestAttempt per Player + Quest, bound to specific snapshot version at start. Multiple independent attempts (replay allowed; grants not consumed). "Continue" resumes selected in-progress using its original snapshot + synced state. "Reset" clears completions for that attempt only (grant/rewards survive). ## Cross-Cutting Risks, Migration, Tests, Overall

**Global risks (from all slices + skepticism):**
- Frozen content/errors for early players (intentional trade-off for offline; mitigate with analytics + author tools + "replay for updated" messaging).
- Client as judge (tamper, bugs) — receipts/hashes/events help; no perfect without reval (which is cut).
- Import fidelity (old no versions, flags only, scattered logic) — synthetic snapshots + facts + manual diff review.
- Authoring velocity vs correctness (forms friction vs "hard to publish bad") — strengthened gates + import plan + measure real usage.
- "Lightweight" economy vs robustness (events add entities but prevent old bugs).
- Scale unknown (21 quests today; design for small-medium but clean boundaries).

**Migration high-level:** One-time jobs for historical grants (as AccessGrant facts), attempts (as QuestAttempt + StepCompletionFacts against synthetic legacy snapshots), coins (as Reward/SpendEvents from old data + reconcile). New system starts clean; legacy visible as "imported" with version notes.

**Conceptual tests / TDD enablers (per slice + global):**
- Property-based: random sequences of offline play (answers, hints, gifts, physical confirms, reset, multi-device), sync, publish during, assert no double/lost rewards, correct projections, frozen rules used, grants respected, no invalid combos.
- Golden from real quests (export 2-3 full page_constructor + simulate playthroughs).
- Idempotency: duplicate webhook, duplicate sync upload, re-publish same content, reset+re-complete.
- Version: old attempt uses old snapshot rules/amounts even after live changes.
- Offline full: play entire sequence (including answer match, hint spend, gift earn, physical confirm) with no network; on reconnect, state converges or corrects predictably; bundle re-dl works for cleared client with in-progress.

- Maintainability: constructor code itself small/readable (no god); domain aggregates have clear invariants enforceable in types/tests; adding future (e.g., NumericRangeRule, photo, branching) costs 1 place not N.

**How this achieves the constraints & "best":**
- **Robustness:** Facts over mutations, snapshots for stability, idempotency everywhere, corrections explicit, tamper hints where possible without violating offline mandate.
- **Maintainability/Readability:** One GameStep shape + small data; event-sourced where money-like or progress; crisp contexts/aggregates; small focused constructor components; all versioned data self-describing.
- **Elegant design:** Content primary, rules minimal data, events as the accounting primitive, publish as the deliberate versioning point, client as capable peer for its snapshot.
- **TDD/SOLID/DRY/KISS/YAGNI:** Property tests from day 1 (invariants as properties); single responsibility (e.g., snapshot for val, events for progress/earnings); DRY via shared shapes/handlers; KISS (data shapes over heavy frameworks for v1; no 14 types, no god WFs); YAGNI (lean baseline + explicit plan for evolution; no photo/branching/real$ now).
- **Vs old Bubble:** Night and day (47 types -> ~12-15 concepts; 1163 imperative UI WFs -> focused aggregates + small handlers; mutable no versioning -> deliberate snapshots; no offline -> first-class PWA; scattered coin/answer logic -> explicit facts + rules; UI state pollution -> clean per-attempt/ snapshot).
