## 2. Deconstruct: The Listed Races + All Intersecting Edges (Timelines + Failure Modes, Grounded)

All assume: single Player + valid AccessGrant; Devices A/B authenticated as player; quest downloaded (same or compatible snapshot unless noted); "Attempt X" = specific QuestAttempt id (creation/sharing across devices itself racy per ANALYZE-05). "Facts" = StepCompletions + coin deltas per locked payload. Old system had *none* of these (always-online mutations via scheduled WFs on shared mutable cards).

### Race 1: Partial sync (flaky reconnect mid-upload; duplicate or lost on retry)
- T0: Device A offline, 5 completions + 2 hint spends pending (local facts + local balance delta -2).
- Reconnect: Uploads batch for steps 1-3 + spend on 1; server records 1-3 + -1 (partial ack? or network drop after server write but before client receive).
- Device A retries full batch (or background sync fires again): steps 1-3 + 4-5 + spends 1+2.
- If no explicit idempotency key (only natural (attempt,step,version) or client_ts): server may re-apply spend on 1 (double deduct if not checked), or upsert overwrites submitted value on step 2 with "later" ts (even if same), or records duplicate StepCompletion rows.
- Coin: local shows -2; server may have -1 or -3. "Reconcile" on next load applies correction (player sees balance jump or "you spent more").
- Version drift mid-partial: during retry, new publish? Old facts carry old snapshot; new ones?
- Outcome: lost (if server dedupes naively on step only) or double (if not); overdraft or "free" hint reveal that shouldn't have been; player confusion on "what actually synced".
- Why locked fails: "idempotent" stated as req (06) but "no explicit idempotency keys yet" (task); upload is "the attempt's StepCompletions" (set, not sequenced log); no client_seq / batch_id / event_id in described payload (03).

### Race 2: Concurrent devices on same attempt (dual offline progress + coin spend + submit)
- T0: Both devices have synced state for Attempt X (v1), at step 3, authoritative player balance=10, attempt spent=0.
- A offline: completes step 4 (answer "foo", local is_correct=true per v1), buys hint step 5 (local -1, reveal), advances. Local: spent=1, facts for 4/5.
- B offline (parallel): completes step 4 (answer "bar", local is_correct=true or false), buys hint step 6 (-1), completes 7. Local spent=1 (diff step), facts 4/6/7.
- A reconnects first: uploads facts (4,5 + spend5). Server records/upserts (4+5), applies -1 → balance=9. "OK".
- B reconnects: uploads (4,6,7 + spend6).
  - Step 4: last-write by ts? B overwrites A's submission (different submitted value or is_correct claim lost). Or "union" keeps both? But per-step is LWW register in current facts model, not set.
  - Spends: different steps → -2 total. Balance=8. But B's local view was still 10 (stale); it spent assuming affordance that A had already eroded.
  - Attempt "current step" (if mutable aggregate): races to max or last-writer.
  - If same step touched (B also buys 5): duplicate spend record or last wins → possible -2 for one step or lost reveal.
- Outcome (per 06 risk): lost submission detail (analytics per version polluted), coin overdraft allowed (player saw two reveals "simultaneously" that global couldn't cover), "current" state arbitrary, corrections on next load for both devices ("your hint on 5 was clawed back?").
- Why fails: "last-write or union" (03:120) ambiguous for non-set data (submitted string not unionable; per-step fact is single row); no device_id + local monotonic seq in payload; coin deltas "applied" without total order or per-op identity; no explicit per-fact idempotency beyond natural key (which assumes "one submission per step ever").

### Race 3: Version drift mid-sync (publish during long offline + continue/re-dl)
- Device A: starts Attempt Y on v1 (answers list A1 for step 2); plays offline to 5, facts recorded locally vs v1.
- Admin publishes v2 (fixes answer in list for step 2; changes a gift_coins amount).
- Device B (or A after clear): "continue" Attempt Y. Server returns Y bound to v1. Client requests bundle for v1.
  - If historical snapshots *not* retained (common simplification, risk noted in 03/07): only v2 served. Client "continues" using v2 rules/amounts for new facts. Old facts from A (v1) coexist on same attempt? Or server rejects mixed? On sync, v1 facts + v2 facts for same (attempt, step)? Analytics mix versions?
  - Gift earn on terminal: uses v2 amount (wrong for the playthrough that used v1 rules).
  - Re-dl for cleared device with in-progress Y: impossible without retention → "progress lost" for offline resume, violating "old attempts remain playable" (03).
- Mid-sync publish: partial facts from v1 upload; new local facts vs v2? Drift on same attempt id.
- Why fails: binding "tied to the specific quest version/snapshot it was started against" (01/03) is fragile without retention policy + enforcement in sync (facts must carry + be validated against the bound snapshot only); "new attempts get new" doesn't protect existing attempt records or their historical facts; coin amounts versioned only if explicitly carried in facts (not in "current" facts upload model).

### Race 4: Coin overdraft correction UX (local optimistic + post-fact server reconcile)
- Balance authoritative=5 (synced). Cached on devices.
- A offline: buys 3 hints (local deducts to 2; reveals 3).
- B (concurrent or sequential before A sync): buys 3 (different steps; local to 2).
- Both sync (order A then B or interleaved): server "applies" -3 + -3 → -1. Or checks per-spend and rejects second batch.
- "A hint spend that would overdraft coins can cause the local attempt state to be corrected on next load" (03).
- UX: Player on A sees 3 hints revealed (spent "successfully" offline), later "balance corrected to X; some hints unrevealed?" or negative shown until next earn. Or retroactive "you couldn't afford hint on step 5 — progress rewound". For earns: two devices complete same quest → double 5-coin unless dedup (old Getting_5 list hack; new "sum" has no equivalent documented).
- Versioned: earn uses snapshot gift amount at time; if correction after publish, which amount?
- Reset during: complete (earn), reset (clear spends?), re-play (re-earn?).
- Why fails: reconciliation is "handwave" ("sum ... minus spends"; "local spends are applied"; "corrected on next load") with no protocol for *when/how* correction is computed/emitted, no compensation events, no UX spec, no prevention (optimistic local always allows if cached >=0); per-attempt spent vs global balance fuzzy (spends in attempt Z after earn in Y?); import of old Balance_coin may already be inconsistent with historical Buy_hint + gifts.

### Race 5: Reset during sync (destructive clear races with concurrent play)
- T0: Attempt X at step 8 on both devices.
- A (syncs): "Reset progress" → client clears local StepCompletions for X; on sync: server "deletes or marks cleared all prior completions for X" (03). Attempt record survives; status InProgress.
- B (offline whole time): played 8→12, spent 2, submitted answers. Local facts advanced.
- B reconnects after (or during) A's reset sync.
  - Hard clear on server: B's upload of 8-12 either re-creates (reset "lost" for the player who reset) or rejected ("attempt reset"); B loses work.
  - Soft (reset_ts marker): B's "newer" facts may union in (defeating reset) or be treated post-reset (reset wins for A but B sees mixed).
  - Devices emit conflicting "reset" markers: non-convergent state.
- "Reset + immediate re-play before sync" interleaves with prior facts.
- Why fails: Reset modeled as "clear ... locally (and on next sync)" (destructive mutation on facts), not immutable operation with epoch/seq; no happens-before vs concurrent facts; "affects only the selected attempt" true but useless under partition; no payload shape for reset in described sync (03).

### Race 6: Import legacy facts (old non-versioned answer_card mutations → new versioned facts + coins)
- Old: answer_cards per (user, page_constructor, quest) with flags only (no submitted text, no version, created/mutated via scheduled create_answer_card_list + quest WFs + 666); coin via global Balance_coin mutated + Getting_5 list (dedup) + per-card Buy_hint; content mutable (page_constructor Answers/Gift_Coins changed post-play).
- Import (per 08 "desired" + "full per-step where feasible"): group cards into synthetic "legacy attempts" (by time/batch countCard/statistic); synthesize v0 snapshot from *current* exported page_constructors at import time (capture Answers list + Gift_Coins + inferred kinds at *import*, not historical play time); map flags → StepCompletion (is_correct=Complited, coins_spent=Buy_hint?1:0, submitted=null "unknown"); set player balance from old Balance_coin (or computed net); attach "provenance: legacy-bubble-import-YYYY".
- Edges: cards reference pages that no longer exist or reordered (gaps in StepCompletions); post-play content edit means mapped "is_correct" may not match v0 list (or vice versa); coin: old Balance may != sum(gifts inferred from You_made_it cards) - Buy_hints (inconsistencies from racy WFs); double-earn or lost on "first only" (list may be incomplete/out-of-sync); multiple cards per "attempt" with conflicting flags (Complited_quest true but not all Complited); no client_ts or device; "reset" in old? (del flag); version drift on import (synthetic v0 != what player actually saw).
- On "continue" imported attempt: re-dl synthetic v0 (if retained); new facts vs v0; old facts mixed?
- Why fails (per ANALYZE-09): "full per-step fidelity *not feasible* at 100%"; "lossy by nature"; "old may already be inconsistent"; "synthetic legacy snapshots" + "quarantine unmapped in legacy_metadata"; "one-time idempotent job" required or pollutes new model; coin reconstruction "hell"; "best-effort summary attempts".
- Additional: no explicit idempotency in import (duplicate runs create dup facts?); corrections/negative from import must be auditable.

**Additional intersecting edges (from siblings + discovery + 07 opens):** Flaky partial + concurrent (worse); reset + import (legacy "reset" via del?); coin + version (earns use frozen snapshot amounts only); analytics per-version (wrong answers submitted vs vN must stay queryable by snapshot, even if vN+1 fixes); physical notes + multi-dev (last wins or lost); "abandoned" set on one dev while other advances; clock skew on client_ts (order?); no audit trail in current facts (cannot replay "exact sequence of submissions/hints" for support or "replay" feature); storage bloat if facts not compacted; background sync while playing (new local fact arrives after partial upload started); cleared client + re-auth (recover from server facts + re-dl exact snapshot for *that* attempt's version); "pending vs authoritative" UI anxiety if corrections frequent.

These are not exotic; they are the *direct* consequence of full offline PWA + multi-device + versioned frozen snapshots + per-attempt/per-step coins + client local val (no reval) + mutable "current facts" recording + "reconciliation" without protocol + old non-versioned always-online mutations as import source. "Last-write or union" + "handwave" + "no explicit keys yet" = invitation to exactly the 06 failure mode.

## 3. Expose: Flaws in the Locked ("Current") Model ("facts upload + server project" baseline)

- **"Last-write or union" is not a strategy (fatal per ANALYZE-05):** Explicitly admitted as needed (03) but undefined algorithm, no conflict UI, no preserved invariants, no handling for non-commutative data (submitted string, per-step is_correct claim, note). Directly triggers "sync logic has races" risk. In practice: silent loss of one device's work on overlap; arbitrary "current" state; polluted per-version analytics (which wrong answer "won"?).
- **Reconciliation handwave (coins):** "master ... = sum ... minus spends"; "local spends are applied"; "corrected on next load". No formula, no timing (earns on terminal record? on gift completion fact?), no dedup for "5-coin" equivalent (old list hack not replaced), no per-op identity, no prevention vs. correction, no versioned amount embedding, no compensation protocol/UX spec. Allows overdraft windows (multi-dev or stale cache); negative or retro-unreveal UX horrors; double-earn on concurrent complete or reset+replay. Per-attempt spent vs global fuzzy.
- **No explicit idempotency keys yet (despite "idempotent" req in 06):** Natural key (attempt+step+version) works *only* under "one submission per step ever" assumption. Fails for: retry after partial (re-apply deltas?), reset+re-complete on same attempt, multi-dev same step, import dups, background sync overlap. Old scheduled WFs had no keys either (races implicit in 1163 WFs).
- **Mutable facts as "current state" (not append-only):** Upload "the attempt's StepCompletions" (set semantics implied) invites overwrites. No causality, no full history for replay/audit/"what the player actually did on device A". Reset as destructive clear is non-atomic/non-idempotent under concurrency.
- **Version drift fragility:** Facts carry version but sync/merge has no enforcement (mixed versions on one attempt?); retention underspecified (without it, old attempts unplayable post-clear, violating locked); earnings may use wrong (live) amounts if not carried in facts.
- **Error recovery non-deterministic + invisible:** "Corrected on next load" (03) — no explicit correction events, no player-visible protocol ("your balance was adjusted because..."), no testability. Partial sync + correction = confusing state.
- **Import pollution risk (per ANALYZE-09):** Legacy facts (lossy, inconsistent, non-versioned, no submitted) injected into same "facts" model as live → either pollutes invariants (e.g. negative from bad old data) or requires special "legacy" paths that accrete complexity.
- **Vs old (anti-pattern confirmation):** Old *had* the "always-online API events + scheduled mutations on shared mutable bag" and still had races/inconsistencies (orphan cards, coin drift, flag conflicts). New "facts upload" is prettier wrapper around similar optimistic mutation + post-hoc reconcile. "We fled the Bubble app to escape" this class (09).
- **Maintainability tax:** Merge/reconcile layer will grow if-statements for every race (reset-during, version-mid, partial+concurrent, coin sign-flips, legacy) — recreates 1163-WF spaghetti. No deterministic fold = hard TDD. Client "current map" vs server facts drift bugs inevitable.
- **Self-critique of locked docs (fresh):** 03 already self-critiques frozen bugs/client-as-truth/retention but *understates* the distributed systems reality for the primary play mode (location quests on phone+tablet, flaky mobile). 06 lists the exact failure as unacceptable yet the only described model (pre-ANALYZE-05) is the racy one. "Idempotent" and "error handling" are should-haves/reqs without protocol. COINS/05/01 siblings already exposed this; this ANALYZE-10 hardens it for the recording surface.

The "current" (Variant 1 baseline) is an optimistic sketch that satisfies the *letter* of offline + no-reval + recording but not the *spirit* of robustness under the races it names. It will produce support load exactly as warned.

## 4. Variants: 4+ (as specified) — Full Cycle Each (Description + Happy/Edge + Harsh Flaws + Self-Critique)

All variants *respect* locked (client local val + record client is_correct claim without server override of correctness; attempt/facts bound to snapshot at start; new=latest/old frozen; sync records + reconciles coins; per-attempt spends + global earn projection; reset on selected attempt only; import best-effort facts; idempotent+eventual; no admin coins). They differ in representation of "the facts", sync payload, merge, idempotency, compensation, determinism, replay/audit.

### Variant 1: Current Facts Upload + Server Project (Locked Baseline from 03/01; "facts as current set")
**Description (grounded):** Client maintains mutable local "current completions map" (or list of latest per step) + local coin delta/cache, all validated against pinned snapshot bundle. On every local action (confirm/answer/hint/gift/advance/reset): mutate the map + aggregates (spent, wrongs, current pos). For sync: POST the *current set* of StepCompletions for the attempt/snapshot (or delta since last known) + net coin effects. Server: locate/create QuestAttempt (bound to snapshot); for each fact in payload, upsert/insert by natural key (attempt, step_pos, snapshot_id) or client_ts (last-write); record submitted + client is_correct as-is (no re-compute); apply coin spends as deltas to master ledger or player balance (or per-attempt spent); compute/reconcile earnings from qualifying facts (gifts + terminal using *snapshot* amounts at emit time); return ack + authoritative aggregates + any "corrections" (e.g. overdraft → adjust local map on next load). Merge for multi-dev: "last-write or union" (per 03) on the fact rows. Reset: client clears map; server deletes/marks facts for attempt. Version: facts carry snapshot; server rejects drift or allows coexistence. Idempotency: assumed via natural key or ts. Analytics: query facts by snapshot. Import: synthesize facts + synthetic v0 snapshot + one-time balance set.
**Happy Path Cycle:** Download snapshot vN → local attempt bound → offline play (map mutates, local val/award/spend) → reconnect: upload current map facts → server upserts facts, reconciles sum(earns from facts) - spends → client pulls authoritative map/balance → "synced".
**Full Cycle + Handling of Listed Races:**
- Partial: retry uploads full current map; server upserts (if ts newer or natural key match, may no-op or overwrite).
- Concurrent devices: A uploads its map slice first (4,5); B uploads (4,6,7) → last ts or "union" (completed set union + last per overlapping step); spends summed or last aggregate.
- Version drift: facts carry v; server stores mixed or enforces per-attempt; re-dl fails if no retention.
- Coin overdraft: apply all reported; if proj <0 emit correction (client map adjusted on next load; possible un-reveal).
- Reset during: clear on one; other's later map upload may re-populate or be post-reset.
- Import: map old flags to facts vs synthetic v0.
**Harsh Flaw Exposure (Skeptical):** Exactly the racy baseline deconstructed in ANALYZE-05 §2-3 and COINS §4: "last-write or union" is "bug invitation"; reconciliation handwave allows double/lost/overdraft with ugly post-correction UX; no explicit keys (natural key insufficient for retries/resets); mutable set loses causality/history (no replay of sequence, which "replay" feature and analytics per-version need); version binding fragile without retention + fact enforcement; corrections invisible/non-deterministic; import injects lossy data into same path. Maintainability: merge logic accretes special cases for every race listed. TDD hard (no pure fold). Vs old: prettier name for optimistic mutation + scheduled-like reconcile. Violates "deterministic" and "no lost/double" in task. "Idempotent" is aspiration, not designed (payload lacks keys/seqs).
**Self-Critique of Variant:** Simplest client (local map easy); matches thin "upload facts" language in 03. But incomplete for the edges *it acknowledges* + explicit 06 risk. High runtime surprise cost. Not ready for impl (as ANALYZE-05 concluded for "current").

### Variant 2: Client Command Log (Append-Only Local Events) + Server Deterministic Apply (Event-Sourced Facts)
**Description:** Every mutating player action is an immutable AttemptEvent (or Coin-affecting fact) generated locally (even offline): {event_id: uuid or (player,device_id,local_seq monotonic), quest_attempt_id, snapshot_version (pinned), step_pos or step_version_id, event_type: 'physical_confirmed' | 'answer_submitted' | 'hint_purchased' | 'gift_claimed' | 'attempt_completed' | 'reset_requested' | 'coin_earn_pending'?, payload: {submitted_value?, local_is_correct?, coins_delta?, note?, client_ts, ...}, prev_event_ref? for chain}. Client: append-only local log (IndexedDB or equivalent) + pure projection/fold function that computes "current map + aggregates + local balance proj" from log tail + snapshot data (deterministic, replayable on every load). On sync: POST {pending_events: [tail since last_acked_server_seq or vector], device_id, attempt_snapshot}. Server: append unseen events (idempotent by event_id; ignore dups/retries; order by (client local_seq + device_id + client_ts tiebreak) or server receive + tie); for each, record StepCompletionFact or CoinEvent (immutable row with event_id, snapshot, all client claims as-is); project authoritative QuestAttempt state + player coin ledger (sum all earns from gift/completion events using *snapshot* gift amounts at event time - all spends); emit CompensationEvent(s) if needed (e.g. overdraft detected post-batch → negative correction or un-reveal fact). Return: acked up to seq X + any new server-side events (corrections, other-device facts) since client's head. Client: append received server events to local log (forcing re-projection on next render). Merge: union by event_id (dedup); deterministic fold on full log for state. Reset: append 'reset_requested' event (with epoch); projection for "current" ignores pre-reset events (or treats post as fresh seq); history preserved in log for audit/replay. Version: every event carries snapshot; projection/facts filtered/enforced to match attempt's bound version. Idempotency: event_id (client-generated, safe retry). Coins: every earn/spend is distinct event (per-attempt spend linked; global earn projection deduped e.g. by unique (player,quest, 'COMPLETION_BONUS', snapshot?) or event_id); snapshot-frozen amounts embedded or resolved at apply from retained snapshot. Analytics: full log or facts queryable by snapshot. Import: one-time job synthesizes minimal event streams from old cards/flags/dates (one 'answer_submitted'/'physical_confirmed'/'hint_purchased' per mappable card + 'legacy_completion' earn events); seed with legacy balance as genesis correction event; attach provenance; idempotent (ON CONFLICT DO NOTHING on event_id or natural keys).
**Happy Path Cycle:** Local action → append event to log → re-project local view from snapshot + log → offline play. Reconnect: upload pending tail → server appends (dedup), projects, returns corrections + other events → client appends, re-projects → authoritative state.
**Full Cycle + Handling of Listed Races (Superior by Design):**
- Partial sync: event_id makes retry pure no-op (server already has it); partial apply still leaves consistent tail; client resumes from acked head.
- Concurrent devices: both append their events (A: submit4, purchase5; B: submit4diff, purchase6, complete7). Server unions all by id; projection folds (policy: e.g. for (attempt,step) take latest client_ts event for "current answer", but *keep all* in log for analytics/replay). Coin deltas summed exactly (no double because distinct events); overdraft: server can reject at append (if online) or emit CompensationEvent post-batch (client re-projects: un-reveal or show "debt until earn").
- Version drift: events carry v1; server rejects events with mismatched snapshot for the attempt; re-dl uses bound snapshot + replays only matching events. Retention: server keeps snapshot manifests + enough for projection (or full for replay).
- Coin overdraft: events additive; projection = fold (deterministic); correction = explicit CompensationEvent appended by server (e.g. "SPEND_REJECTED" or "BALANCE_ADJUST"); client log has it; UX: "balance corrected because concurrent spend on other device; hint on step 5 now unrevealed (or you owe 1 until next gift)". Clear, auditable. Dedup for bonus: unique constraint or "has prior earn event for (player,quest,kind,snapshot)" before emitting.
- Reset during: A appends reset event (epoch++). B appends progress events (with their seqs). On merge: projection for current starts after latest reset (B's pre events preserved in log for "what I did before reset?"); post-reset B events treated as new play or flagged. Deterministic > destructive clear.
- Import: synthetic events (idempotent insert); genesis correction for old Balance; future events only per new rules; legacy attempts marked; "continue" replays synthetic log against v0 (limited fidelity).
**Harsh Flaw Exposure (Skeptical):** Higher initial complexity (local log + shared pure projector spec between client/server; event schema; retention for snapshots + logs). Ordering under partition: client_ts skew requires stable tiebreak (device_id + local_seq primary); clock issues still exist but don't lose data. Projection lag: client/server must implement *identical* fold (golden tests mandatory; drift = different "current step" views until full sync). Reset semantics decision still needed (same-attempt epoch vs. "reset retires attempt + auto new attempt" — latter cleaner for "independent attempts" invariant). Storage: logs grow with retries/wrongs (but tiny vs 5MB; snapshot projections + prune old with care). "No reval" preserved (client claim in event payload; server never recomputes correctness from live). Still trusts client for is_correct claim (receipts from OFFLINE-01 can layer for audit). May be "overkill" if concurrency rare (but problem states "full offline PWA" + multi-dev as primary).
**Self-Critique of Variant:** Directly satisfies "replay/merge" (task + 05 title), "immutable event-sourced completions", "easy replay/merge", "idempotent sync of completions/coins", "no lost/double", "clear corrections". Eliminates every listed race via append + id + deterministic fold (no silent loss; union of *all facts*; compensation explicit). Preserves all locks (client claim recorded; snapshot binding per event). Audit/analytics per version first-class (query events by snapshot). Maintainability: "merge logic" = "append + fold" (far less special-case than V1); testable (pure functions). Ties GAMSTEP (events record claims vs frozen GameStep rules/amounts in snapshot) + COINS (per-attempt spend events + global earn projection; snapshot-frozen gift amounts resolved at apply) perfectly. Import: clean "synthesize events once, idempotent". Vs old: *antithesis* of scattered mutations (facts, not flags in WFs). Higher conceptual load than "just upload map" but the complexity is *essential* (problem space), not accidental. This is the direction siblings already converged on (05 V2 strong rec; COINS V3; OFFLINE C'; SYNTH/FINAL "event facts + compensation").

### Variant 3: CRDT for Progress/Completions/Coins (Conflict-Free Merge)
**Description:** Represent *state* (not just history) with CRDTs so independent replicas (devices + server as replica) mutate locally and merge converges without central sequencer or loss. Examples: completed steps = OR-Set (or G-Set + tombstones/epoch counter for reset support); per-step submission = LWWRegister<{submitted, is_correct, ts, device}> or MV-Register (keep conflicts); hint purchases = OR-Set<(step, spend)>; per-attempt aggregates (spent, wrongs) = PN-Counter or better per-device G-Counter summed (or set of spend events for exactness); global coins = separate CRDT (PN-Counter deltas or set of earn/spend ops, or CRDT + ledger); version pin + reset epoch = LWWRegister + counter. Client: local CRDT replica + snapshot for val; mutate on action (add to sets, LWW assign, increment counters); local projection for UI. Sync: exchange state (or ops for op-based) or deltas with server; server merges into canonical CRDT (or acts as last replica); clients pull merged. Merge commutative/associative/idempotent by construction. Coins: delta ops or earn/spend sets (sum unique); snapshot amounts in CRDT state or attached. Reset: remove-observed or new epoch counter (future ops tagged). Version: LWW or tagged. Idempotency: CRDT merge. Analytics: final converged state (weaker than log); or layer op log. Import: seed CRDT state from old flags.
**Handling Listed Races:** All become "apply ops from both; merge produces convergent state". Overlap on step: LWW by ts/device or MV (UI chooses/prompts). Reset: epoch op converges without destroy race. Coins: delta ops or sets prevent double-apply of same op; overdraft still possible (no central choke) but structure doesn't lose a spend; correction via later op. Version: LWW pin; conflicts surface. Partial: merge deltas idempotent.
**Harsh Flaw Exposure:** Overkill/YAGNI for linear quests + low-concurrency human play (classic case where simple LWW + explicit conflict UI suffices 99%; CRDT buys math at high cost). Impl error-prone (subtle bugs in "simple" sets per literature); need equivalent client (TS/WASM) + server (Rust?) impls or shared protocol. State size: tombstones for reset/remove grow; GC complex. Debugging: "why step 5 completed?" requires CRDT math, not reading events. Coins global not naturally pure per-attempt CRDT (crosses aggregates → reintroduces reconciliation layer). Replay/audit weak (final state, not ordered history of submissions/hints; "replay" feature needs extra log anyway → hybrid event+CRDT). Semantic conflicts remain (which conflicting answer "counts"? Policy needed on top of algebra). Still needs snapshot binding + retention + versioned amounts. Vs locked: formal convergence better than "last or union" but adds accidental complexity on top of essential (version pin, offline, coins, no-reval). "Deterministic" yes (merge), but maintainability poor without mature lib + expertise.
**Self-Critique:** Excellent formal guarantees for offline-first convergence (no lost updates within model). But mismatch for domain size/access pattern (small fixed steps, "usually one device at a time"). Practical cost high; likely resume-driven. Can be sub-component (e.g. CRDT for hint set) or future opt, not primary. Hybrid with V2 (events as ops feeding CRDT state) possible but not KISS.

### Variant 4: Strict Server Projection with Client as Pure Cache + Compensation Events
**Description:** Client is cache + offline simulator only; never owns recorded truth. Online: *all* actions (submit/confirm/buy/claim/reset/complete) sent as commands to server (with local seq, client_ts, submitted + local_is_correct claim from snapshot sim). Server owns QuestAttempt aggregate + ledger: validates grant/access/snapshot pin, applies transition (records fact with client claim, no correctness override), projects state, returns new projected state + side effects (earns, reveals) + any prior corrections. For full offline: client runs *full local simulation* against pinned snapshot (immediate feedback, complete playthrough, local cache deduct/award); *queues* sequence of commands (local seq, the exact claim). On reconnect: send queued command seq (idempotent via attempt+client_seq or command_id); server applies *in order* (or merges if multi-dev), using payloads (record client is_correct claim); checks/applies coins against authoritative proj at apply time (reject or compensate if overdraft). Attempt state on server = source of truth; client polls/pulls or gets updates on load/continue. Reset: explicit server command; atomic clear or marker. Version: server enforces match on commands. Idempotency: server-side seq/command id. Compensation: explicit events returned/applied to client cache (e.g. "SPEND_REJECTED on seq 7; re-sim without reveal"). Analytics from server facts. Import: seed server state/facts.
**Handling Listed Races:** Server sequences (receive or client seq); second on same step no-op or additional per policy; coins checked at apply (second overdraft rejected/corrected immediately in response). Reset command applied; post-reset queued cmds from other dev dropped or rebased. Version: server owns binding; re-dl tells client exact snapshot needed. Partial: re-send unacked from seq; server acks. Import: server-side facts.
**Harsh Flaw Exposure:** Fights locked "full offline" philosophy + "client validates its version fully" (03/08): long offline works for *sim* but recorded truth/coin effects "pending" until sync; player can complete offline, see "earned 5!", go offline again, later discover earn not granted or spend clawed ( "pending vs authoritative" anxiety everywhere — exactly the tension the no-reval lock tried to remove by making client local-val the truth). Queue replay complexity: reset-then-replay-10-steps in queue must replay in order; if server moved (other dev), rebase/conflict handling sophisticated (error-prone). Latency: every step roundtrip or reliable flush (tensions "disappear into the city" value prop). Still needs log for history/replay (otherwise "replay what player did" lost). If server *does* re-compute is_correct on apply (using retained snapshot), violates no-reval lock; to respect, blindly trusts client claim (back to trusting client for permanent records, just via server write). Corrections still needed for offline batches.
**Self-Critique:** Safest for coin invariants (central choke + authoritative at apply) and "no lost" (server serializes). Maps to reliable queues + outbox + command handler. But creates exactly the "sync pending" friction the offline model (03) was chosen to eliminate. Requires reopening/nuancing the "client as truth for version" lock or accepting provisional anxiety. Good for strict server projection but not KISS with the full-offline mandate. Hybrid with V2 (queue of events/commands applied deterministically) viable.

## 6. Recommendation for Robustness (No Lost/Double, Clear Corrections), Maintainability (Deterministic), KISS

**Primary Recommendation: Variant 2 (Client Command Log / Append-Only Local Events + Server Deterministic Apply + Explicit Compensation Protocol) as the core recording model. Layer tamper-evident receipts/hashes from OFFLINE-01 where they add audit value without violating no-reval. Make this the *enforced* shape for business/01/03/08 updates. Hybrid elements from V4 (server as sequencer for online paths) acceptable but secondary.**

**Rigorous Why (after full cycle + cross to all grounded sources + siblings):**
- **Robustness (no lost/double + clear corrections):** Eliminates *every* deconstructed race via append-only + event_id (idempotent by construction, no silent overwrite), deterministic fold/projection (all facts kept; policy explicit e.g. "latest ts for current view per (attempt,step); union for analytics"), compensation as first-class appendable events (visible, replayable, auditable — "your hint on step 5 corrected because concurrent spend on device B at ts X; balance now Y"). Coins: per-attempt spend events + global earn projection with snapshot-frozen amounts (ties GAMSTEP/COINS); dedup via event_id or (player,quest,kind,snapshot) unique; overdraft produces explicit Compensation not mysterious negative. Version: carried + enforced per event. Partial/merge/reset/import: convergent without loss. Matches "no lost/double, clear corrections" bar exactly; superior to V1 handwave, V3 numeric weakness, V4 provisional anxiety.
- **Maintainability (deterministic):** "Merge = append + fold" (pure, testable, no ad-hoc ifs for races). Client/server share (or compile from) exact projector spec → no drift. Invariants crisp (facts immutable; projection = fold(log, snapshot); every earn/spend attributable to event + version). Vs V1's inevitable spaghetti merge layer; better long-term than CRDT math or queue rebase.
- **KISS (under constraints):** Happy path still "play locally (append + project from snapshot), push tail on reconnect, pull corrections, re-project". Adds essential machinery (log as source, not current map) justified by the *essential* complexity of offline+multi-dev+coins+versioned+replay (not YAGNI). Starts lean (events only for mutating actions; narrative implicit in pos). Avoids V3 overkill and V4 tension with locked full-offline/client-val. Directly implements the prelim in FINAL + recs from 05/04/01/09.
- **Ties to GAMSTEP/COINS recs (explicit):** GAMSTEP: events/facts record *client's local claim* (is_correct from snapshot rules) for the bound version; server never overrides correctness (no-reval); amounts for gifts from the GameStep data in *that* snapshot. COINS: per-attempt spends as events on StepCompletion/AttemptEvent (1:1 with hint buy); global earn reconcile as projection over RewardEvents (emitted server-side on authoritative recording of gift/terminal completion fact, using snapshot gift_coins); "first-only" via existence/unique on (player,quest,kind); corrections explicit; import seeds historical facts once (idempotent). Snapshot-frozen everywhere. "Sum earnings - spends" becomes deterministic fold, not handwave. Matches SYNTH/FINAL "events as accounting primitive".
- **Payload shape (explicit, for impl):** Client upload: {attempt_id, snapshot_id, device_id, last_acked_server_seq?, pending_events: [{event_id, local_seq, type, step_pos, payload: {submitted?, local_is_correct?, coins_delta?, note?, client_ts}, prev_hash? (optional chain)} ] }. Server response: {acked_up_to: {seq, event_ids}, new_events: [server Compensation or cross-device facts], authoritative_projection: {current_step, spent_this_attempt, status, balance? (or separate coin endpoint)}, corrections_applied: [...] }. Facts stored: immutable rows with event_id PK, all fields + server_received_at + snapshot_id.
- **Merge rules (per-(attempt,version,step) deterministic):** 1. Union all events by event_id (dedup across devices/retries). 2. Order for projection: primary (local_seq per device + device_id lexical) or (client_ts + tiebreak); server may total-order on receive for online. 3. For "current" view (UI): per (attempt, step, type) take the event with highest order key (LWW register semantics for submitted/is_correct); keep *all* in log/facts for analytics/replay/audit. 4. Reset: latest 'reset_requested' defines epoch; current projection ignores pre-epoch events (or starts new seq). 5. Coins: fold = sum(all positive earn events for player with matching snapshot rules) - sum(all spend events); per-attempt spent = sum(spends linked to attempt). 6. Version: only events with snapshot == attempt's bound are folded for that attempt's state; others quarantined or error. 7. Idempotent: ignore duplicate event_id on append.
- **Compensation protocol (explicit, UX-auditable):** On server apply of batch: compute post-batch proj; if any spend would have made negative given prior authoritative (or policy), or duplicate earn detected, or version mismatch: append CompensationEvent(s) to the attempt's log (type: 'spend_rejected' | 'balance_adjust' | 'hint_unreveal' | 'earn_revoked' | 'legacy_correction', payload: {affected_event_id?, reason, delta, prior_balance, new_balance, snapshot}). Return in response. Client: append to local log, re-project (UI shows banner "Sync correction: hint on step 5 could not be afforded due to concurrent activity; it is now hidden. Balance adjusted from 2 to 5."), persist. Player can view attempt "event history" (replay) including corrections. Negative only via explicit genesis import corrections or admin-audited (but no manual per 08). Clear, no silent.
- **Test properties (TDD from day 1, property-based + golden):** 1. For any finite sequence of local events E (incl. answers with values, hints, gifts, physicals, resets, concurrent simulated devices) on snapshot S: replay(log) produces identical final completions map, is_correct claims (per S rules), revealed hints, net coin delta as server authoritative projection after "sync". 2. Sync idempotent & convergent: uploading same/ overlapping tails (any order, any interleaving of failures/retries/partials) results in *exactly* same set of facts + same final projection (modulo deterministic corrections). 3. No lost/double: every client-generated event appears at most once in server facts; every earn event for (player,quest,kind,snapshot) emitted at most once (unique constraint); projection never negative except explicit import corrections. 4. Version fidelity: facts/events for attempt always carry exactly its bound snapshot; projection uses only matching; new attempt always gets >= prior latest published at creation time. 5. Reset: append reset event; current projection post-reset has no pre-reset completions/spends; prior history preserved in full log; new facts post-reset independent. 6. Coin: earnings for attempt use *only* gift amounts from its snapshot's GameStep defs (never live); "first-only" bonus deduped globally per (player,quest) or per-version per policy. 7. Import: after synthetic events from legacy cards + genesis correction, projection matches (or audited diff) old Balance + flags; no double with future events; legacy attempts marked. 8. Corrections visible + deterministic: any overdraft race produces CompensationEvent(s) in log; re-project after append reproduces the corrected state on client and server. 9. Partial + multi-dev: after any partition + reconnects, both clients' local projections (after incorporating server new_events) equal server's authoritative. 10. Analytics: all submissions (incl. wrong answers, different device claims) queryable grouped by snapshot; never mixed across versions. Fuzz: random quest snapshots + random valid/invalid sequences + random partitions + random publishes mid-play + random resets + random clears/re-dls; assert all hold. Golden: take 2-3 real old quests (export page_constructor), simulate full playthroughs (physical/answer/hint/gift), assert projection + facts match expected from old behavior where mappable, but use new rules.
- **Concrete required changes (do not ship sync without):** 1.
