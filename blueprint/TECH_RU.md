# ТЕХ

## Снапшоты и версионирование
- Явное действие Publish создаёт новую неизменяемую версию (снапшот) квеста.
- Снапшот содержит полный упорядоченный список GameStep с:
  - Всем богатым контентом.
  - Простыми списками допустимых ответов (для клиентского матчинга в оффлайн).
  - Замороженными значениями поддержки (подарочные монеты, стоимость подсказок и т.д.).
  - Изображениями комиксов / ссылками на медиа.
  - Данными навигатора и ссылками на анимации (если есть).
- Новые попытки и новые скачивания всегда получают последнюю опубликованную версию на момент запроса.
- Старые попытки навсегда остаются привязанными к той версии (снапшоту), с которой они начали.
- Исторические снапшоты (или минимум данных, необходимых для их повторной материализации) должны храниться на сервере бессрочно для любой версии, у которой ещё есть активные или недавно сброшенные попытки в процессе. Это позволяет игроку заново скачать точный бандл, если он очистил локальные данные.
- Публикация — это осознанное действие. Это не то же самое, что просто переключение флага «published» на изменяемом контенте (антипаттерн старой системы).

## Событийно-ориентированный прогресс и монеты
Все игровые действия, завершения, заработок монет и траты записываются как неизменяемые факты/события только для добавления (append-only):
- AttemptFact (или StepCompletionFact): записывает, что именно сделал игрок на конкретном шаге внутри конкретной попытки, привязанной к конкретному снапшоту.
  - Типы включают: physical_confirmed, answer_submitted, hint_purchased, gift_claimed, attempt_completed, reset_requested и т.д.
  - Payload несёт локальное утверждение клиента о результате (local_is_correct), отправленное значение (когда применимо), coins_delta, заметку, device_id, локальный порядковый номер, клиентскую метку времени.
- CoinFact (узкий реестр): записывает каждое движение монет (GIFT, COMPLETION_BONUS, HINT_SPEND, RATING_SPEND, LEGACY_CREDIT, CORRECTION).
  - У каждого факта есть ключ идемпотентности (attempt + step + kind + snapshot).
  - Сумма со знаком.
  - Замороженная исходная сумма копируется из привязанного снапшота в момент создания факта.

Текущее состояние QuestAttempt и мастер-баланс монет игрока не мутируются напрямую. Они являются детерминированными проекциями (fold) лога фактов.
- Клиент поддерживает локальный лог событий + идентичную проекцию в оффлайн.
- При подключении: клиент загружает ожидающие факты; сервер добавляет их (идемпотентно), проецирует авторитетное состояние, возвращает коррекции при необходимости (например, обнаружен овердрафт → подсказка отменена и баланс скорректирован).
- Факты с разных устройств чисто мержатся по ключу (union). Конфликтующие раскрытия разрешаются правилом «один раз раскрыто — остаётся раскрытым».
- Политика проекции для текущего вида: per-(attempt, step, snapshot) last-write-wins с использованием (client_ts + device + local_seq). Полный лог сохраняется для аудита, повтора и аналитики.
- Сброс попытки: по умолчанию создаёт свежий независимый ID попытки (история остаётся на старой для повтора/аудита). Накопленные глобальные награды и грант выживают. Факты выбранной попытки очищаются для новой проекции.

Этот подход переживает все известные гонки (игра с двух устройств, сброс concurrent с игрой, дрейф версии + повторное скачивание, чередование earn/spend монет, долгий оффлайн, сдвиг часов) без потерянных или двойных наград и без героической логики мержа.

## Модель оффлайн PWA
- Игрок скачивает самодостаточный бандл ~5 МБ для конкретного снапшота.
- Бандл должен позволять полное прохождение всей последовательности в отключённом состоянии:
  - Рендер шагов по 4 шаблонам.
  - Локальная валидация ответов против встроенного plain списка acceptable.
  - Физические подтверждения (доверие + явное «Я сделал»).
  - Покупка подсказок через попап неправильного ответа (локальное списание монет + раскрытие).
  - Данные навигатора (если есть).
  - Анимированные/озвученные награды бонусов.
  - Локальная проекция баланса монет из замороженных подарков + локальных завершений.
- Клиент — единственный судья корректности для скачанного снапшота. Сервер никогда не перепроверяет результат при синхронизации — он только записывает то, что утверждал клиент.
- Service worker + Cache API + IndexedDB для оффлайн-ассетов и локального лога событий.
- При подключении клиент синхронизирует факты и получает авторитетные коррекции (чётко отображаются игроку: «синхронизация...», «баланс скорректирован»).
- Индикатор «Режим оффлайн» пока есть ожидающие факты.

## Разделение клиент vs сервер
- Клиент: полная локальная валидация + проекция + delight UI (анимации, голос, немедленная обратная связь) против своего снапшота.
- Сервер: долговечный append-only лог фактов, проекторы, поддерживающие read-модели (текущее состояние попытки, баланс игрока, аналитика per-version), коррекции, когда локальное provisional-состояние было неверным, хранение исторических снапшотов.
- Сервер записывает отправленное клиентом значение и утверждение клиента о local_is_correct. Он не переопределяет исход игрока для этой версионированной снапшота.

## Коммерция и доступ
- У игрока должен быть валидный пожизненный AccessGrant (или квест должен быть бесплатным), прежде чем он сможет создать попытку или скачать любой бандл.
- Источники грантов (с аудитом): успешная оплата, погашение купона, бесплатный квест, грант администратора.
- Гранты идемпотентны (максимум один на player+quest).
- В v1 только покупка одного квеста (без корзины).
- Купоны — это процентные скидки (поддерживаются разные проценты; 100% купон = бесплатно через купон).
- Бесплатные квесты используют идентичную механику с платными (просто добавляются в коллекцию, price 0 или явный флаг is_free).
- Гранты переживают обновления контента (новые версии не отзывают существующий доступ).

## Подход к конструктору
- Lean форма + упорядоченный список как база.
- Немедленный structured ввод данных для корректности (особенно ответы и подарки), потому что опубликованные снапшоты заморожены для оффлайн-игроков.
- Пикер 4 шаблонов, который pre-fill-ит разумные дефолты (текст кнопки, копия подтверждения и т.д.).
- Structured AnswerListEditor (чипы/строки + хелпер «Вставить строки») + live «Test match» бокс, который запускает ту же клиентскую функцию матчинга, которая будет в бандле для этой версии.
- Dedicated subform для подарка (нарратив + число монет + заметка, что значение замораживается в снапшоте).
- Зоны загрузки комиксов по ролям (task, character, hint, atmosphere) + thumbnails.
- Конфиг навигатора (geo picker + toggle «включить кнопку навигатора (опциональная подсказка)») на физических шагах.
- Назначение ассетов анимации/голоса для бонусов заданий.
- Wiring попапа подсказки (по умолчанию для заданий с ответом).
- Per-step mini-превью с использованием настоящих shared player-компонентов (против текущих значений черновика).
- Pre-publish гейты валидации + чеклист (должен быть primary комикс на Task-шаблонах, валидное количество ответов и т.д.) + опциональный «dry-run serialize».
- Явная большая кнопка Publish, которая создаёт неизменяемый снапшот и триггерит материализацию бандла.
- «Сохранить + переключиться на реального игрока как тестового пользователя» приемлемо для финальной валидации (упражняет реальный PWA, реальную попытку, реальные монеты из этого снапшота, реальный sync, реальный оффлайн после скачивания).
- Вкладка импорта (вставка YAML/JSON или файл) как power-user путь, который парсит, валидирует и загружает в список композера.
- Каждый publish создаёт новую версию. Редактор всегда работает с «следующим» черновиком. Опубликованные квесты сохраняют свои исторические шаги для активных попыток.

Цель для кода конструктора самого по себе — маленькие, сфокусированные, heavily typed компоненты с shared рендерерами между админом и плеером.

## Факты как унифицирующий примитив
Прогресс, движения монет, траты подсказок, использования навигатора, триггеры анимированных бонусов, mid-quest FeedbackReports и траты на рейтинг — всё выражается как факты/события.
Это даёт:
- Повтор / аудит («какой был баланс на дату D?»).
- Детерминированный мерж на multi-device и после долгого оффлайна.
- Чёткий учёт («этот подарочный шаг в vX наградил 10, потому что было записано это завершение»).
- Лёгкую аналитику per-version (отправленные неправильные ответы, использованные подсказки, клики навигатора, репорты по шагу).
- Путь импорта, который может синтезировать исторические факты один раз (идемпотентная задача) вместо попыток reverse-engineer разбросанных старых мутаций.

## Миграция из старой системы (высокий уровень)
- Старые гранты (buy_a_qest + платежи + купоны + free + списки пользователя) → факты AccessGrant + проекции.
- Старые данные answer_card + списки пользователя + Balance_coin + Getting_5... + Gift_Coins из page_constructor + countCoinMadeIt квеста → синтетические legacy-снапшоты (контент на момент экспорта) + StepCompletionFacts + CoinFacts (по возможности сохранять отправленные значения и приблизительные timestamps).
- Одноразовая идемпотентная задача. После импорта новая система чистая. Legacy-элементы помечены «imported». Старый scalar баланс сверяется через diff лога (ручной review, без auto-adjust).

## Базовые non-functional требования
- Ожидаемый размер бандла ~5 МБ (изображения + occasional 10-30s видео + structured контент + теперь также роли комиксов, данные навигатора, refs анимации/голоса). Должен быть переоценён с реальными ассетами.
- PWA должна поддерживать полную игру в оффлайне и graceful degradation на low-end устройствах.
- Нет обязательств по GDPR / хранению данных.
- Скорость роста неизвестна — проектировать сначала для small-to-medium масштаба с чистыми границами.
