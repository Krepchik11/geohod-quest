## Cycle on the Report: Deconstruct (Missed Error Surfaces or Velocity Issues)

However, under the "relentless critical analyst" mandate, several error surfaces and velocity issues are under-called or missed relative to cross-slice invariants (especially post-synthesis GAMSTEP hybrid + offline frozen model + 5MB snapshot reality):

- **Locked "save+test player" + GAMSTEP rules data entry friction (missed amplification):** Report correctly notes preview iteration loop = "minutes per tweak" for 15-25 step quests (grounded in ~26.5 avg from 556/21 in discovery). But it under-weights the *interaction with GAMSTEP data shape* (from ANALYZE-03 + SYNTHESIS-NOTE: refined lean `completion: { mode: 'physical' | 'answer'; acceptable?: string[]; allow_note?: bool }` + `supporting: { gift?: {coins: number; narrative: string} ... }`). A missed surface: author changes mode (physical <-> answer) after populating answers list or gift coins → silent or late mismatch at serialize (report calls "kind + answers mismatch" but not the roundtrip cost when the shape is now "rules data" per GAMSTEP). For gift coins (tied to snapshot per COINS + 04:40): entering a number in a generic field vs. explicit "this value freezes for vN earnings" has no authoring-time surface in pure lean. Velocity hit: to verify "my gift step will award exactly 5 coins from this snapshot" or "my answer list serializes without blanks into the Completion data", author must save + full player test + (for coins) complete prior steps to observe balance effect. Report's "locked acceptable" accepts this, but cross with offline (03:118 "frozen answers per version") + coins races (from ANALYZE-04) makes every missed authoring guard a permanent per-version liability. 5MB quests (08:57, 03:35: "images + occasional 10-30s videos") add: media upload in form gives no bundle-size estimate or "this video will bloat the PWA cache for offline players" warning before publish.

Report notes this in deconstruct but does not call the compound risk: authors will avoid full end-to-end tests for media-heavy quests, shipping answer lists that "look ok in textarea" but produce client match surprises (or empty-match dead-ends) in the 5MB bundle.

- **Publish snapshot size / bundle gen implications for 5MB quests (missed surface in lean + composer):** Report (§2, §7) correctly says lean "directly" supports bundle (working steps → serialize at publish). But for ~5MB (media dominant), the constructor has no visibility into "what the publish flow will actually pack" (resolved refs? dedup? cache headers? total size warning?). In lean: media "upload succeeds silently; step list may show filename only". In V4 composer invention: thumbnails + "mini-preview" but no "est. bundle impact" or "media role validation for offline" (primary vs hint vs video 10-30s). - **"Locked save+test player" + no high-fid at launch + "hard to publish bad" (06 success criteria) tension (under-exposed as velocity/quality killer):** Report deconstructs it well (§1.116, §2.138: "fidelity low for the exact things that cause errors"; "authors skip full tests, ship subtle UX/text bugs that are frozen"). Missed surface: "save+test" tests *integration* (real PWA, real coins from prior gifts in this quest's snapshot, real map) but not *authoring ergonomics for the data that freezes* (parsed answers list, exact geo pin on mini-map in context of hint spend, media load in bundle cache, gift award UI at the exact moment in linear seq). ## Cycle on the Report: Expose (Flaws in Its Variants)

Report's variants are well-defined and critiqued internally. Lean (V1) is correctly positioned as decision-compliant MVP baseline with highest maintainability *if disciplined*. Richer preview (V2) correctly attacked for sync complexity + scope violation of "no high-fid at launch" (08:39) + "preview is easy to say and hard to build" self-critique (04:95). V4 composer invention is the "evolutionary" rec with strong "why" (templates + structured + gates attack the exact hotspots).

Flaws exposed (harsher than report's internal cycle; does "acceptable" preview decision + lean create unmaintainable authoring UX long-term?):

- **Lean form+list + acceptable preview:** Report claims "Highest of variants" for maintainability of *constructor code* (§2.144: "small surface: list + StepEditor ... no preview sync logic"; "Risk of regression to unmaintainable: if ... giant switch(14 kinds)"). This is correct vs old (55/63 WFs of per-Page_type conditionals + self-refs + 444 SetCustomState in reusables; 36-field bags; duplication of page/page_constructor). But the *product authoring UX* long-term: lean + external test *does* risk unmaintainable *experience* (not code). For internal team, if velocity data (post-MVP measurement called for in report) shows authors batching changes and skipping tests on 5MB media-heavy quests, the org will add "side tools" (external sheets synced via import, custom scripts, or "just edit the DB snapshot" hacks). This recreates accidental complexity outside the "small readable constructor" (exactly the pathology of old: authoring lived in 55/63 reusables while admin page was thin). "Acceptable" decision + pure lean makes the "hard to publish bad" (06) failure mode cheaper for authors than doing the right thing. Long-term: the constructor surface accretes "preview affordances" anyway (violating the original lean intent), but in an ad-hoc way because the baseline provided none. Report acknowledges ("plan to evolve") but does not call this "UX debt" as a first-class maintainability risk for the *product*, not just the code.

- **Richer integrated preview (V2):** Report's skepticism is good (§3.167: "state for sim attempt ... resizable split or modal — responsive pain"; "Divergence risk if preview renderer forks"; "Violates the 'no high-fid... at launch' decision"). Additional flaw: even "using exact same player components" creates a *second execution environment* for the GameStep data (draft vs real attempt + real AccessGrant + real multi-quest coin balance + real PWA SW cache + real device geo). Old system had per-type Slide_* duplication (e.g. Slide_Question 12 WFs, Slide_Error 21 WFs, Slide_give_prize 8 WFs in element_definitions) precisely because "preview" or "edit render" forked from player. V2 re-introduces that fork risk under modern components (useEffects for "sim vs real", fake coin providers leaking). For frozen content: high authoring fidelity is seductive but authors may over-trust the sim for the exact 5MB offline case (report calls it). "Save+switch" remains mandatory for release; V2 adds cost for marginal gain on the "acceptable" axis.

- **Import-first / low-UI (V3):** Report strong (§4: "Best avoidance" of old complexity; "parsed/validated model can be the canonical"; "roundtrippable for audit"). Flaw not fully exposed: for a mixed internal team (devs + content people, as report notes "if ... not text-inclined, V3 will be shelfware"), primary import creates *dual maintenance surface*. If forms/list also exist (as fallback or for light edits), you now have "text source of truth" vs "DB draft steps" sync problem — exactly the old "page vs page_constructor" duplication (identical 556 recs) and "quest vs quest_name_constructor" the report correctly rejects. YAML/JSON escaping for Russian multiline texts + media refs (in 5MB context) is error-prone at authoring time. "Light editor" after parse still needs to produce the exact GAMSTEP shape or the bundle path diverges. Good for migration (ANALYZE-09 synergy: transform old page_constructor → YAML → import), but as *primary* for ongoing authoring it risks the "low discoverability" becoming a velocity tax that forces forms anyway.

- **Library/composer invention (V4):** Report's self-skepticism is excellent (§5.276: "richer than 'acceptable MVP' ... adds scope (templates, map embed, dnd lib, validator, structured answer component, mini previews)"; "For a true minimal launch it may be too much — risk of delaying the ... success criteria"; "can be staged"). Additional exposed flaw: "templates as first-class" (Physical Observation Task, Answer/Knowledge, Gift/Reward, etc.) risks recreating a light taxonomy (old 14 Page_type values drove specialized reusables + conditionals). If templates proliferate to match real variety from 556 steps (or from 14 old values: questionnoanswer for physical, gift, lead, video, congratulations, etc.), the "StepEditorPanel ... switches on template/kind" becomes the new conditional god (even if typed discriminated unions). "Mini per-step using shared player renderer" is DRY win *if* the shared component is built first and strictly data-only; otherwise it leaks attempt state or preview-mode hacks into the player (maintainability backslide). "Pre-publish gates + dry-run serialize" is the highest-leverage part (directly supports "hard to publish bad" + bundle correctness), but in a full composer it is UI chrome that can be added to lean without the palette/DnD/minis. Does it create unmaintainable long-term? The code can stay readable *if* components-per-kind + pure validator fn are enforced; the risk is "feature creep on authoring delight" once internal team uses it daily.

**Does "acceptable" preview decision + lean create unmaintainable authoring UX long-term?** Yes, on the *experience* axis (not the initial code surface). The decision was made under "small internal team" + "MVP velocity" assumptions (08, 04 self-critique). Under the frozen-snapshot + offline client-as-judge model (03/08), every authoring error that reaches publish has permanent cost. Lean + external test makes catching those errors *more expensive than making them*. Long-term: either (a) content quality plateaus low (bad for revenue/reviews), (b) team builds parallel authoring paths (import scripts, Google Sheets + transform, direct snapshot edits) that duplicate the "constructor" logic outside the maintainable surface, or (c) the lean surface accretes the V4 pieces anyway (in uncontrolled order). The report's hybrid rec (lean base + immediate V4 data/gates) is the correct mitigation, but the "acceptable" lock makes the baseline itself the source of future pressure.
