## Goals / Non-Goals

**Goals:**
- Pure deterministic per-version stats projector(s) (grants count per quest from grants store; attempts/completion rate + per-step wrongs/hints/nav/feedback from facts logs of attempts bound to the snapshot/version via manifest + project_analytics reuse or extension; completion rate = attempts with attempt_completed fact / total attempts for snap; mirrors client project* + marketplace grant idemp/source logic exactly; order-independent additive folds).
- Thin FeedbackReport list (read-only per quest/version for authors): collect FeedbackReported facts (with step_position, note, device_id, local_is_correct) from all attempts bound to the matching snapshot (or quest via published meta); mid-quest attach step context already in fact; no mutation, no edit.
- Admin visibility surface: small focused components (stats cards showing grants/attempts/completion%/per-step counts; FeedbackReportsList read-only table or list per selected quest/version; 100% reuse snapshots/goldens for versioned content display like primary comic/template in marketplace; narrow 'use client' island or RSC fetch per react agents; enhance landing/ctor or narrow new co-located files; no god).
- TDD goldens contract first (RED for stats computation on happy+extra-edges facts + grant/attempt/completion correlation + feedback listing cases in replay or backend tests, then impl to green); client/server invariants (pure fold always accurate; idemp facts prevent inflate on reconnect/concurrent; snaps freeze versions for historical attempts).
- Backend minimal: in-mem store extension (additive reverse index snap_id -> Vec<attempt_id> on bind, or pure scan for YAGNI small N; pure fns in facts or thin admin module; read-only handlers for stats + feedbacks list; reuse AppState locks/grants/fact_logs/published; routes additive e.g. GET /api/admin/versions/:snapshot_id/stats and /feedbacks or quest-scoped; explicit "Future: trait + persist swap" like facts/grants; no new Cargo deps; rust.md strict (pub docs + examples on all, Result, #[cfg(test)] AAA, 4-space, clippy -D, no prod unwrap).
- 100% reuse facts/snapshots/goldens (no dupe fold logic; extend/use project_analytics + existing snap bindings/manifest/grants; goldens drive TDD for stats/feedback flows + corr with grants/attempts; player FeedbackMenu + facts append unchanged).
- Strict agents (rust.md: docs on pub, #[test] mods, 4-space, no unwrap, Result; react.md: RSC by default or narrow client, small comps <100LOC, derived in render, narrow deps/effects, explicit conditionals, no barrels/inside-comps, no waterfalls); TDD/SOLID/DRY/KISS/YAGNI; quality gates (replay green + grant/attempt/compl corr + stats/feedback cases, cargo test/clippy/fmt -D, frontend build/lint, reuse greps, manual admin views + stats accuracy + feedback mid-quest + publish version + reconnect).
- Survives races (stats during active attempt/version publish: pure recompute from current idemp facts + snap bindings always correct/current; concurrent feedback appends: lock serializes + natural_key idemp no dupe counts; multi-device facts merge for stats: idemp union + additive fold accurate (wrongs/hints per step once or count correctly); feedback for historical version: bound snap determines version, old attempts stay on their snap; version publish while attempts active: new attempts on new snap, stats separate, grants on quest independent).
- Verifiable: after impl, replay + cargo tests green (new stats/feedback cases + corr + prior goldens untouched), frontend build+lint clean, manual (backend running; play/feedback mid-quest on golden -> admin stats reflect counts + Feedback list shows step+note; grants + post-grant attempts correlate in stats; publish new version -> separate stats; reconnect facts no inflate; read-only for "authors").

**Non-Goals:**
- No persistent admin data or separate FeedbackReport store (in-mem or simple extension of existing fact_logs + grants; documented swap path like facts/grants; restart loses transient views but facts re-sync via player gives accurate recompute).
- No advanced analytics/UI (basic counts/cards + list only per PLAN YAGNI + Phase 4 "surfaced"; no charts, export, filters, real-time, per-player, time-series; small comps).
- No mutable scalars/rows for stats (pure fold from facts sole source; violates prior cycles invariants if mutable).
- No god admin (small separate surface; no dupe logic from projectors/grants; reuse/extend only).
- No quest_id on Fact or attempt (YAGNI; use snapshot_id as version key + PublishedMeta/grants quest_id for correlation; demo goldens use snap id as quest key; future additive).
- No server-side FeedbackReport separate append (reuse unified Fact + facts append; client already emits mid-quest; read via list).
- No real-money adjustments, external authors, GDPR/deletion, branching, advanced answer norm, high-fidelity preview, etc (per PLAN explicit cuts + briefing).
- No changes to player flows, grants creation, facts append semantics, goldens data, or prior projectors (additive only; all fidelity preserved).
- No full /admin route or auth (internal demo surface in landing or ctor; client "author" view read-only).
- No new crates or bloat (enhance existing patterns/files).

## Decisions

**Decision: Per-version key = snapshot_id (from attempt manifest binding); quest correlation via PublishedMeta (quest_id + snapshot_version) + grants (quest-level); grants count at quest, versioned usage (attempts/completion/per-step) at snap.**  
Rationale (after deconstruct): PLAN "Per-version stats (grants, attempts, ... FeedbackReports per step)" + "List of FeedbackReports per quest/version"; grants are lifetime on quest (survive versions per marketplace design/SPEC); attempts bind permanently to the exact snapshot they started (TECH "Old attempts remain permanently bound to the exact version"); facts carry no quest (unified thin per facts-sync decision, YAGNI to add now). Using snap as primary version key for stats/feedback list reuses existing manifest/attempt_snapshots + project_analytics without model change. Grants counted by quest (from InMemoryGrantStore) for "grants" in per-version (or per-quest view). PublishedMeta provides quest->snaps mapping for UI. Pure fold/scan over small in-mem maps is KISS and accurate.  
Alts considered & rejected: 
- Add quest_id to every Fact/append (breaks 100% reuse + prior goldens/player emit; violates YAGNI + additive-only from briefing; would require player/ctor changes).
- Mutable stats rows per snap/quest (exposed harshly: race on concurrent facts/feedback, lost accuracy on version publish, can't correct/replay from facts, violates "facts sole source" + idemp from facts-sync/marketplace/reconnect cycles).
- Full separate FeedbackReport entity + store now (dupe append logic, mixes with facts, YAGNI per facts-sync "stick with thin unified"; briefing "FeedbackReport thin append-only (like facts)").
- Global stats only (no per-version: useless for frozen snapshots per PLAN risk "frozen bad content lives forever ... per-version analytics on ... reports per step").
Self-crit of this choice: survives? Yes — reuses snap bindings/manifest/grants/published exactly (DRY, fidelity to prior cycles), pure/accurate via idemp facts, small additive, TDD via goldens replay on snap-bound facts. Flaw: real published quests may have quest_id != snap base (e.g. "mystery-v2"); mitigated by PublishedMeta (quest_id + snapshot_version) + list-by-quest in admin UI; tasks cover manual + future quest filter. Demo goldens use "mystery-fortress-v1" as both. In-mem scan ok (N attempts <<100 per quest).

**Decision: Pure projector fns (e.g. project_version_stats(snap: &str, fact_logs: &HashMap<..>, grants: &.. , manifests: &..) -> PerVersionStats { grants: count by quest, attempts: count bound, completions: count with AttemptCompleted, per_step: fold analytics + group by step_position for wrongs/hints/etc from Feedback etc } ); reuse/extend project_analytics; list_feedbacks_for_version collects FeedbackReported enriched with attempt/snap context.**  
Rationale (deconstruct): PLAN/TECH "projectors for ... per-version analytics"; "facts as sole source" + "deterministic projections"; prior facts-sync implemented project_analytics exactly for this (hints_used, wrongs_submitted on !correct answer, navigator_clicks, feedback_count) + tests cover feedback edges. Pure fold (no side effects, idemp-safe since upstream dedup) guarantees correctness even mid-play or post-reconnect (recompute from current log always right; no lost updates on version publish). Per-step: simple group-by in fold (or Vec per step) for "FeedbackReports per step" + wrongs/hints/nav counts. Grants separate (quest) but correlated in struct. List: filter attempts by manifest snap, then filter facts for FeedbackReported variant (already carries step_position + note). Mirrors marketplace "reuse 100% existing snapshots/facts/goldens (no dupe logic)".  
Alts rejected: 
- Mutable counters updated on append (races, inaccuracy on corr/replay/version publish, violates pure + facts source from all prior cycles).
- Client-side only stats (no server admin visibility for authors; multi-device incomplete; server authoritative per TECH).
- Scan every time in handler without pure fn (dupe code, hard to TDD/reuse in tests).
Self-crit: survives? Yes — pure like project_state/balance (testable, no drift, order-indep for counts/sets), extends existing analytics (DRY), 100% reuse (facts for usage, snaps for versioned), TDD goldens first (RED asserts on counts from happy+edges facts + corr with grants). ## Risks / Trade-offs

[Scan or reverse index over attempts for per-snap stats/feedback list on every admin read] → Mitigation: N tiny (quests <10 steps, demo attempts <<50); pure fn + short lock; index additive (O(1) lookup); YAGNI until measured (tasks note "profile if >100 attempts/quest"); facts idemp ensures counts never wrong even if scan races with append (lock serializes).

[No quest_id on facts/attempts (snap as version proxy may collide real quest/version ids)] → Mitigation: PublishedMeta carries quest_id + snapshot_version (from ctor publish); grants by quest; admin UI can list by quest then pick version/snap; demo goldens use snap id as key (fidelity); future additive quest binding on publish/append without breaking.

[In-mem admin views (and fact/grant stores) lose on backend restart/deploy] → Mitigation: explicit documented swap path in store (same as facts-sync + marketplace-grants designs: "Future: trait ... impl for Jsonl/Sqlite (no behavior change)"); player reconnect + facts re-append (idemp) + pure fold recompute gives identical accurate stats/feedback list; TDD unaffected; demo re-play easy; tasks require manual "restart + reconnect verify stats same".

[Stats during active play or mid-quest feedback concurrent with list read] → Mitigation: pure fold recomputes from current log (always correct post-idemp); lock in handler serializes append + read (short crit, no await); natural_key prevents dupe counts on reconnect; per-step feedback attaches step at emit time.

[Version publish while attempts active + stats for historical vs new] → Mitigation: attempts stay bound to their original snap forever (manifest); new attempts get latest; stats/list per-snap separate (old frozen content has its usage/feedbacks; new version its own); grants on quest independent (per marketplace design).

[Feedback mid-quest for historical version read by authors (context may be incomplete without full snap)] → Mitigation: fact carries step_position + note (sufficient per SPEC "attaches current step"); list returns with snap context; authors can cross-ref snapshot from published/goldens (reuse); full snap optional in manifest (future).

[Admin surface "god" or dupe snapshot logic] → Mitigation: small comps only (AdminStats/FeedbackList modeled on MarketplaceList/FeedbackMenu <50LOC); 100% import getSnapshot/goldens for versioned content (derive comic/summary exactly like marketplace); parent (page) owns fetch/state; explicit reuse greps in gates.

[Goldens drift or incomplete coverage for stats/feedback + grant/attempt corr] → Mitigation: RED first in replay (failing asserts on counts/list/corr before any admin code); extend happy + edges (already has feedback/nav/wrong/hint); backend tests inject same + assert; manual + gates enforce; prior fidelity preserved.

[Scope creep to mutable stats, advanced UI, real persist, quest_id on facts, server feedback split] → Mitigation: explicit YAGNI + cuts in proposal/tasks; pre-impl grep gates (no "mutable|advanced|persist for stats|quest_id on Fact"); self-crit at end + tasks.

Trade-off YAGNI vs robustness: chose pure fold + in-mem scan/index + snap-as-version-key + enhance small comps + goldens RED over "perfect" (dedicated analytics DB, full quest model, separate FeedbackReport, advanced dashboard, persist from day 1). This still survives every edge in PLAN/SPEC/TECH/briefing (idemp facts sole source for accurate stats, mid-quest feedback, per-version frozen, races via pure+lock+idemp, 100% reuse) and produces immediately verifiable TDD + manual against goldens. Enables future (Phase 4 polish/measurement, real persist, ctor admin views) with zero rewrite of core fold/append.
